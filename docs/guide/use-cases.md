# 实用案例:不同情境下如何组合技能

> 配套 [README.md](README.md)(技能清单)阅读。图中 `→` 表示执行顺序/转交;`+` 表示可并行或按需穿插。技能名均为安装后目录名。

## 组合速查表

先按「你手里有什么 → 你要什么」粗选:

| 你手里有什么 | 你要什么 | 组合 |
|---|---|---|
| 只有一个想法/口头描述 | 一套可递交的申请文件 | `patent-intake` → `patent-drafting` → `patent-drawings` → `patent-compliance` → `conversion` |
| 现成材料(论文/PPT/DOCX) | 同上(先摄入) | `conversion`(摄入)→ 走上行链 |
| 材料 + 只想交代理机构 | 一份技术交底书 | `patent-intake`(交底分支)→ `conversion` |
| 产品外观照片/渲染图 | 外观设计申请 | `patent-intake` 外观分支(`design-points.md`)→ `patent-compliance` → `patent-filing` |
| 已经写好的草稿 | 递交前把关 | `patent-compliance`(+ `conversion` 交付 Word) |
| 已写好、要递交/收到补正 | 流程指引 | `patent-filing` |
| 审查意见通知书 | 意见陈述书 | `/skill:patent-prosecution` → `patent-oa-response`(+ `patent-claim-strategy`) |
| 驳回决定 | 复审请求书 | `/skill:patent-prosecution` → `patent-re-exam` |
| —(要打别人专利/ defend 自己专利) | 无效请求/答辩 | `/skill:patent-prosecution` → `patent-invalidation` |
| 实用新型/外观授权专利 | 维权前评估 | `/skill:patent-prosecution` → `patent-evaluation-report` |
| 一份权利要求 | 范围/修改/分案/优先权策略 | `/skill:patent-prosecution` → `patent-claim-strategy` |
| —(任何阶段) | 先有技术检索 | `patents-search`(US/EP)+ CNIPA 手动检索(`search-guide.md`) |

## 一、自助申请链路(B 组)

### 案例 1:发明人从零申请发明专利(完整链)

**情境**:发明人只有一个技术方案(比如一种新的数据处理方法),能接受访谈,目标是递交一套发明专利申请文件。

**组合**:

```text
patent-intake(三轴路由 + 四要素访谈:技术问题/最小可实施方案/区别特征/技术效果)
    → patent-drafting(删除测试定必要特征 → 独权 → 上位化阶梯 → 从权退路;再五段式 + 摘要,支撑链内闭环)
    → patent-drawings(流程图/结构图,标记双向一致,摘要附图)
    → patent-compliance(支撑链/清楚性/形式自检,报告落 草稿/检查报告.md,零未决 critical)
    → conversion(草稿/ → 成品/申请文件/*.docx,三份同名 docx)
    [用户请求时] → patent-filing(电子申请注册/缴费/流程)
```

**要点**:

- 路线记录(`草稿/申请信息.md`)与阶段清单在 intake 阶段落定;类型吃不准时读 `patent-intake/references/type-decision.md`,**一案两请**(发明 + 实用新型同日)在类型轴上明确记录后再进入撰写。
- `patent-drawings` 需要环境有 `dot`(Graphviz);没有则该技能 fail loud,不假装出图。
- 交付走 `conversion` 的降级链(python-docx → pandoc → 手动),全不可用时交付降级报告而非假 Word。
- 想先摸底先有技术再写背景技术:在访谈阶段穿插 `patents-search`(见案例 7)。

### 案例 2:现成材料(论文/PPT/DOCX 交底)转实用新型申请

**情境**:团队有一份内部技术评审 PPT 和一篇论文,想直接申请实用新型。

**组合**:

```text
conversion(docx/pptx 摄入:保源文件与提取笔记进 .patent/materials/)
  → patent-intake(统一来源处理:归档+提取-确认-补齐,五标志入档;论文/PPT 是技术输入,不自动等于交底完整)
      → patent-drafting → patent-drawings → patent-compliance
        (各自走实用新型分支:形状/构造限定,不保护方法)
  → conversion(Word 交付)
```

**要点**:

- **摄入在前、路由在后**:intake 的路由表规定「任何用户提供材料 → 先按 source-modes.md 归档摄入,再访谈」。源文件留在 `.patent/materials/`,不混入 `草稿/`。
- 论文不自动算先有技术,也不自动算完整交底——四要素缺什么补访什么。
- 实用新型不保护方法/配方/材料本身;若方案本质是方法,类型判定会把用户推回发明或劝止,不硬写。

### 案例 3:只要一份技术交底书(交代理机构或内部评审)

**情境**:公司流程要求先出交底书,申请文件以后由代理机构写。

**组合**:

```text
patent-intake(交付目标 = 仅交底书)
  → disclosure 分支,按 references/disclosure-document.md 单一合并结构组装
  → conversion(成品/技术交底书.docx,一份合并 docx)
```

**要点**:

- **不制造**权利要求和法定章节来填版面——交底分支明确禁止。
- 交底书是唯一走「单文件合并交付」的产物;申请文件套件是分文件 docx(见案例 1)。
- 若同一材料「两者都要」(交底 + 申请文件):先完整走申请文件链,再组装交底书,不把交底当申请文件用。

### 案例 4:外观设计申请

**情境**:产品外观定型,有六面视图照片/渲染图,想申请外观设计专利。

**组合**:

```text
patent-intake(类型 = 外观设计)
  → 外观分支(references/design-points.md:外观要点访谈 + 视图清单)
  → patent-compliance(外观分支自检:视图规则/图片质量)
  → patent-filing(外观图片递交要点)
```

**要点**:

- 外观视图规则**单一版本**在 `patent-intake/references/design-points.md`,`patent-drawings` 不重复(视图材料由发明人提供,该技能只管发明/实用新型的制图)。
- 不写权利要求、不写五段式说明书——外观分支不产出这两样。
- 法律锚点按需读 `patent-standards/references/cn-design.md`(2026-08-12 对 CNIPA 全文核实)。

### 案例 5:草稿已写好,只做递交前把关

**情境**:用户自己(或别处)已写好权利要求书/说明书草稿,要递交前检查 + Word 交付。

**组合**:

```text
patent-compliance(只查所请求的交付物:支撑链/清楚性/形式,报严重度/位置/修复指引)
  → conversion(Word 交付)
```

**要点**:

- 不必走 router 全链——自检技能可独立消费现成草稿。
- 自检发现 critical 未解决时,把阻塞项退回发明人,不静默代填。
- 若修复涉及重写权利要求,再回 `patent-drafting`(修权项与补落点在同一技能内闭环),或经 `patent-intake` 路由回边。

### 案例 6:递交操作与补正通知

**情境**:申请文件已备好,要实际递交;或递交后收到补正通知书。

**组合**:

```text
patent-filing(注册/数字证书/递交/缴费 + 费减;递交后:受理/初审/公开/实审流程)
[收到补正] → patent-filing 补正协议(常见补正项 + 超范围红线 + 期限)
```

**要点**:

- 该技能标注哪些步骤**只能申请人本人**完成(注册、缴费等),agent 不代办。
- 补正的红线是**不超范围修改**;超出常见补正项清单的改动要先停下来说明,不擅自改文本。
- 撰写阶段默认**不加载**该技能(intake 递交阶段:仅当用户请求时转交)。

### 案例 7:撰写前的先有技术检索(可选穿插)

**情境**:写背景技术前想摸一下现有技术,或想初步判断新颖性。

**组合**:

```text
patents-search(Valyu 语义检索;US/EP 全文)+ CNIPA 手动检索(patent-intake/references/search-guide.md)
  → 结果与引用进 .patent/(sources/ 引用清单, queries/ 检索记录)
  → 背景技术只写三类素材:发明人已知方案 / 客观通用问题 / 检索真实返回
```

**要点**:

- 检索是**可选工具、流程不依赖**:没有 API key 或没有网络,撰写照常进行,背景技术退回「发明人已知 + 客观通用问题」两类。
- **CN 覆盖不保证**:Valyu 官方专利源仅 USPTO 与 EPO;要查 CN 现有技术走 CNIPA 公布公告系统的手动检索指引。
- 检索结果绝不编造、绝不凭记忆补专利号——这是全包的诚实红线。

## 二、专业授权链路(A 组)

> 入口 `patent-prosecution` 是 **user-invoked**,需显式 `/skill:patent-prosecution` 触发。入口先问清手里有什么材料、类型、期限(最多 4 问),期限写在转交记录顶部;闸门不过(输入缺失)就 fail loud,不带病分发。

### 案例 8:答复审查意见通知书(OA,旗舰场景)

**情境**:代理人收到一份审查意见通知书:引用两篇对比文件,指出权利要求 1 无创造性、权利要求 3 不清楚。

**组合**:

```text
/skill:patent-prosecution
  → patent-oa-response(解析通知书:类型/期限/逐条缺陷/法律依据/对比文件
      → 逐条归类 → 三步法重建创造性论述(指南 II-4 3.2.1.1)
      → 策略选择:仅陈述意见 / 改权利要求 / 改说明书 / 更正
      → 修改范围与禁反悔检查 → 逐条意见陈述书草稿 → 人审闸门)
  [修改策略吃不准] + patent-claim-strategy(改 vs 论的阶梯、退路权衡)
  [核对对比文件] + patents-search / CNIPA 手动检索(证据委托检索)
```

**要点**:

- 输入闸门:通知书(优先 PDF)+ 申请文件(权利要求 + 说明书);缺则明说缺什么。
- 对比文件与先有技术只来自真实检索或用户材料;纯文档纪律,无脚本无内置检索。
- 产出是**给人审的草稿**——所有人审闸门之前都只是 draft。

### 案例 9:驳回后提复审

**情境**:申请被驳回,决定在法定 3 个月窗口内(法 41.1)提复审。

**组合**:

```text
/skill:patent-prosecution
  → patent-re-exam(逐条挑战驳回决定;三步法重述论点
      → 修改仅限消除驳回决定/复审通知指出的缺陷(细则 66)
      → 程序:形式审查 → 前置审查 → 合议审查 → 复审决定;撤回(细则 68);不服 3 个月内起诉(法 41.2))
```

**要点**:

- 复审是「对 OA 论点的再论战」,纪律与 `patent-oa-response` 同源;输入闸门要求 **OA 历史**一并给。
- 修改面被细则 66 收窄:只能消除被指出的缺陷,不能借机重构权利要求;想大改另走案例 12 的策略技能评估。

### 案例 10:无效宣告(进攻与答辩双向)

**情境 A(进攻)**:竞品专利挡路,想发起无效宣告。
**情境 B(答辩)**:自己的专利被提起无效,要写答辩意见陈述书。

**组合**:

```text
/skill:patent-prosecution
  → patent-invalidation
      方向 A(请求书):理由限定在细则 69.2 封闭清单内 + 证据登记册
      方向 B(答辩):核对理由与证据 → 反驳(含对创造性理由的反向三步法)
        → 权利要求修改受细则 73 窄限(不得扩权;发明/实用新型不改说明书附图)
  程序纪律贯穿:口审(细则 74)/ 1 个月理由证据期限(细则 71)/ 禁反悔审查 / 撤回(细则 76)
  [取证] + 委托检索(patents-search / CNIPA 手动 / 用户提供)
```

**要点**:

- **双向是同一技能的两个方向**,不是两个技能;入口按请求/答辩分派。
- 理由必须在细则 69.2 的封闭列举之内——清单外理由直接判不可准入,不硬凑。
- 证据检索全部委托/外部,包内无检索无 key。

### 案例 11:实用新型维权前的评价报告

**情境**:公司持有实用新型专利,发警告函/起诉前想做维权前评估;或被控侵权方想反过来请求报告。

**组合**:

```text
/skill:patent-prosecution
  → patent-evaluation-report(谁可请求:专利权人/利害关系人/被控侵权人,细则 62
      → 条件核查:授权后 / 2 个月内作出 / 同一专利权只作一份 / 可查阅复制(细则 63)
      → 证据角色:侵权纠纷审理中的证据(法 66.2)+ 开放许可义务(法 50.2)
      → 如何读 CNIPA 的新颖性/创造性评价(指南 V-10 3.2/3.3))
```

**要点**:

- 报告由 **CNIPA 作出**,技能只指引请求与解读,不代写报告。
- 报告**不是行政决定、不可复议/诉讼**——解读时如实告知其证据地位。
- 报告结论不利时的后续(如无效进攻)由入口显式点名下一站技能(见案例 10)。

### 案例 12:权利要求策略咨询(独立纪律)

**情境**:不针对某份通知书,而是要权衡保护范围、决定是否分案/要求优先权;或 OA 答复中修改方案难定。

**组合**:

```text
/skill:patent-prosecution
  → patent-claim-strategy(必要特征权衡 → 上位化层次 → 权利要求分层 → 退路布防;
      OA 下的修改阶梯与禁反悔感知;分案(细则 48-49)与优先权(法 29-30)及期限决策)
  [新申请的机械撰写] → 转 B 组 patent-intake(策略产出定方向,B 组落笔)
```

**要点**:

- 该技能**只做策略**;把策略写成权利要求文本是 B 组 `patent-drafting` 的活——「策略在 A,落笔在 B」。
- 布局/FTO/许可等组合级问题超出范围(ADR-0007 决策 7),如实告知边界。

### 案例 13:跨阶段串联(评价报告不利 → 无效准备)

**情境**:案例 11 拿到的评价报告对己方不利,想评估无效该专利的可行性。

**组合**:

```text
/skill:patent-prosecution
  →(主任务)patent-evaluation-report 解读报告
  →(入口显式点名下一站)patent-invalidation 方向 A:理由准入初筛 + 证据缺口清单
```

**要点**:

- 入口的规则是「跨阶段的情境,先路由主任务,再显式点名后续技能」——不做一次性大杂烩。
- 证据缺口(缺哪些对比文件/公知常识证据)如实列出,凑不齐不硬上。

## 三、横向组合规则

1. **`patent-standards` 是所有法律断言的单一来源**:任何技能写到法条/指南条号,按需读共享目录核实过的锚点,不复制进用户文稿;条号拿不准就说「以官方为准」。
2. **`conversion` 一技能两用**:Stage-1 材料摄入(案例 2)与 Stage-5 Word 交付(案例 1/3/5),同一降级链,`草稿/` 与 `成品/` 永不混放。
3. **`patents-search` 可插在任何阶段**(撰写前摸底、OA 核对对比文件、无效取证),但永远是可选外部工具;CN 现有技术走声明外部源的手动检索。
4. **入口不调入口**:router 与 prosecution 互不转交;A 组收到「全新申请」显式指回 B 组,反之 B 组不处理授权后文书。
5. **人审闸门贯穿 A 组**:所有 pleading 草稿到人(代理人/发明人)审阅并递交之前,只是草稿。
6. **诚实红线无例外**:不编造现有技术、专利号、文献、实验数据;期限从通知书/决定书里读,不凭记忆。
